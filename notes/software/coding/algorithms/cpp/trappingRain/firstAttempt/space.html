Space

Summary

Since `tpIndex` is the only structure that scales with input size, and everything else is a fixed, small number of variables, the total auxiliary space (not counting the input array itself, which we don't count when discussing space complexity of an algorithm) is: $$O(n) + O(1) = O(n)$$

Breakdown

The vector tpIndex, built by getTowerPeakIndices, stores the index of every peak found in towerHeights. In the worst case (a zig-zag array like $1,0,1,0,1,0,...$), roughly every other element is a peak, so tpIndex can hold up to $~\frac{n}{2}$ entries. Since constant factors drop out in Big-O, that's O(n) space — proportional to the input size.

Everything else:

  • getPIndexOfNextHighestPeak only allocates a couple of local variables (`nextHighestPeak`, `nextHighestPIndex`) — fixed-size regardless of input.

  • getTrappedWaterBetweenPeakssimilarly just uses a few local scalars (`currentTPIndex`, `nextHighestTPIndex`, `minPeak`, `trappedWater`).

  • TrappedWater itself just tracks `nextHighestPIndex` and `runningSum` — again constant space.

None of these allocate any data structure that grows with n; they just do arithmetic on values already sitting in `tpIndex` or `towerHeights`.
