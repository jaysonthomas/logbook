Discovery

Analogy

Imagine you enter a busy party where you don't know anyone, but you are looking for people who want to talk about **robots**.

Instead of going up to a front desk manager (there is no central ROS 1 Master here), you stand near the entrance and shout to the whole room: "Hi everyone! I just arrived. I'm Node A. You can reach me directly at Phone Number 555-1234."

The Multicast shout (Participant Discovery)

When a node is launched, the underlying middleware instantly broadcasts a tiny ping packet over UDP Multicast.

Multicast acts like a megaphone broadcast across the entire room (the local network). Every other ROS 2 node running on that network is tuned into the exact same frequency.

A ping simply says: "I exist! My name is Node A, and here is my exact IP address and port number."

The Direct handshake

Every existing node on the network hears the multicast ping.

If Node B hears Node A shout, Node B saves Node A's phone number (IP address/port). Node B then sends a direct unicast message (a private text message) back to Node A: "Hey Node A, I heard you! I'm Node B, and here is my direct IP and port so you can talk to me directly."

At this point, both nodes know each other exist.

Trading Lists (Endpoint Discovery)

Now that Node A and Node B can send private messages directly to one another, they trade their interest lists (their Publishers and Subscribers):
  • Node A says: "I am subscribing to a topic named `/test`".
  • Node B says: "I am publishing to a topic named `/test`".

The Match & Direct Connection

Node A's middleware compares its wishlist against Node B's offers:
  • Do the topic names match? Yes.
  • Do the data types match (`std_msgs/msg/String`)? Yes.
  • Are the Quality of Service (QoS) rules compatible (e.g., reliability settings)? Yes.
Because everything matches, they shake hands. Node B starts sending topic messages directly to Node A over shared memory or point-to-point UDP, completely bypassing the multicast megaphone.
