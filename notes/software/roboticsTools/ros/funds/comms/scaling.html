Scaling

Node awareness

Because ROS 2 uses a fully decentralized discovery protocol (PDP/RTPS), there is no central server keeping a secret directory. Every node announces its existence over UDP Multicast, so every running node listens to these announcements and builds an internal list of all other active nodes and their capabilities.

Within the Same Domain: Every node tracks the IP address, port, topics, and QoS profiles of every other node on the same `ROS_DOMAIN_ID`.

If Node A is set to `ROS_DOMAIN_ID=0` and Node B is set to `ROS_DOMAIN_ID=1`, they use different multicast ports and are completely blind to each other.

Problem

While total awareness works great for small setups (e.g., a single robot with 15 nodes), having every node talk to every other node scales poorly in massive systems (e.g., a factory floor with 50 robots) because:
  • Multicast Traffic Noise: Constant discovery pings saturate Wi-Fi networks.
  • Memory Footprint: Every node must allocate RAM to store the metadata of every other node in the network.

Solution

To prevent total awareness in large deployments, Discovery Servers (available in Fast DDS and Cyclone DDS). Instead of shouting pings to every node over multicast, nodes report only to a centralized Discovery Server, isolating nodes so they only know about the specific peers they actually need to talk to.

Comparison to ROS1

In ROS 1, a central coordinator (`roscore`) was mandatory for the entire network to function. With a ROS 2 discovery server, a client-server architecture is used for discovery, but it differs from ROS 1 in how data transport and reliability are handled.

Similarities to ROS 1

  • Central Point of Contact

    • Nodes no longer use UDP multicast to broadcast their existence to the whole network. Instead, every node connects to a known IP/port of a designated Discovery Server to register its publishers and subscribers.

  • Selective Network Awareness

    • Just like in ROS 1, nodes only learn about the specific peers they actually need to talk to, drastically reducing multicast noise and saving RAM on edge devices.

Differences from ROS 1

ROS1 relies on roscore:
  • Protocol: Uses XML-RPC over TCP for control and negotiation.
  • Data Transport: ROS Master helps set up custom `TCPROS` or `UDPROS` sockets.
  • Redundancy & Fault Tolerance: Single point of failure. If `roscore` dies, no new connections can be formed.
  • Active Connections: If `roscore` crashes, existing connections survive, but state recovery is minimal.
ROS2 uses discovery server:
  • Protocol: Uses standard DDS RTPS protocol over UDP/TCP.
  • Data Transport: Uses DDS peer-to-peer data transport (including Shared Memory, UDP, or TCP).
  • Redundancy & Fault Tolerance: Highly redundant. You can run multiple backup Discovery Servers in parallel; nodes automatically sync with secondary servers if one goes down.
  • Active Connections: Fully integrated into DDS; nodes dynamically reconnect to backup servers without losing active data pipelines.
ROS 2 Discovery Server gives the network efficiency of ROS 1's central directory without inheriting the fragility or proprietary protocols of ROS 1.
