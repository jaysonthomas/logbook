Composition

Background

One process can run multiple nodes. Likewise, one process can spawn multiple CPU threads.

What determines how many threads run inside a component process is the Executor, not the component container itself.

Overview

Composition is the process of running multiple nodes as components within a single process (rather than separate processes) to reduce overhead. This is especially important for intraprocess communication to avoid serialisation costs on things like image/pointcloud data.

A component is a dynamically loadable node. It is a C++ class inheriting from rclcpp::Node compiled as a shared library (.so or .dll).

Mental model: A node can be written as its own separate program (own process, own PID). Composition loads several node classes into a single process instead — like merging five employees into one shared office instead of five separate buildings. Less overhead, faster communication between them.

Traditional Nodes vs. Components

1 Node = 1 Process.

If 5 separate standalone node executables are launched, the OS creates 5 separate processes. Because each process has an isolated memory space, communicating between them requires shared memory allocations (/dev/shm) or local loopback networking.

Component Composition

Multiple Nodes = 1 Process.

When using components, 1 single OS process (called a component_container) is launched. Multiple shared library components (Node A, Node B, Node C) are then loaded into that single process.

Relation to threads

How components relate to threads depends entirely on which Executor spins the container process.

SingleThreadedExecutor

If a component container uses a SingleThreadedExecutor, 1 single OS thread handles Node A, Node B, and Node C. The single thread loops through callbacks sequentially regardless of which component owns the callback.

MultiThreadedExecutor

If a container uses a MultiThreadedExecutor, the executor creates a pool of OS threads (e.g., 4 threads).

Threads are not assigned 1-to-1 to components. Instead, any free worker thread in the pool can pick up and execute an incoming callback from Node A, Node B, or Node C as data arrives.

A single component could have multiple callbacks executing across different threads simultaneously if its callback groups allow it.
