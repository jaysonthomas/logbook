Scenario

[Ref: drake/examples/hardware_sim/example_scenarios.yaml]

The top-level key is just a name — a scenario file can define multiple named scenarios. One is picked at load time. Everything under it maps onto a C++ struct called Scenario.

scene_graph_config

Configures Drake's SceneGraph.

default_proximity_properties.compliance_type: "compliant" tells the contact/collision engine to treat contacts as compliant (soft, spring-like) rather than rigid by default — this affects how Drake's hydroelastic contact model behaves.

Directives

This is Drake's model directives — a declarative list of instructions for assembling a MultibodyPlant scene, instead of writing C++ calls to AddModelFromFile etc. Each list item is one instruction.
  • add_model

    • Loads a model file (URDF or SDF) and gives it an instance name. default_joint_positions sets the initial joint angles for that model.

    default_free_body_pose sets the initial pose for a model that's not welded (the bell pepper, free to move/fall). The odd key flush_bottom_center__z_up names a specific anchor/reference frame convention on the pepper body (bottom-center, z-up) rather than its geometric origin.

  • add_weld

    • Rigidly fixes a child frame/body to a parent frame/body.

  • add_frame

    • Defines a new named coordinate frame.

    !Rpy { deg: [...] }: A YAML tag (the !Name syntax) tells Drake's parser to deserialize this into a specific drake C++ type, here RollPitchYaw.

Model drivers

It decides how a given model instance is actually controlled/driven in the simulation.

E.g., !IiwaDriver attaches Drake's simulated Kuka iiwa control interface (position control, LCM command/status channels matching the real robot's API) to the iiwa model. !SchunkWsgDriver does the same for the gripper. This is what lets the same scenario file be used to drive either simulation or real hardware with matching interfaces.
